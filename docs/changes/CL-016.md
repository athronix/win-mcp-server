# CL-016 三个小缺口补齐（v0.13.0）

> 日期：2026-11-27 · 承接 CL-011~015 的已知边界清单

## 1. `browser.cdp.attach`（L1）——复用真实登录态

之前 CDP 只能 `launch` 一个独立 profile，代价是没有登录态。补上的是一条正路：

```jsonc
{ "port": 9222 }   // 用户自己带 --remote-debugging-port=9222 启动的浏览器
```

实现：读 `/json/version` 确认端点存在 → 记住端点 → 丢掉旧连接，下一次调用重新附着。
失败返回 `PROVIDER_UNAVAILABLE`，消息里直接写出排查方向：

> 端口 9222 没有可用的 DevTools 端点（fetch failed）；请确认浏览器是以
> `--remote-debugging-port=9222` 启动的，且没有已在运行的实例

**为什么强调"先彻底退出"**：Chromium 单实例模型下，已有实例在运行时新进程只把参数转给旧实例然后退出，
调试端口不会打开——这是最常见的踩坑点，所以写进能力描述而不只是文档。

风险定 L1 而不是 L2：它不改任何东西，只是连上去。**但**连上之后 `act`/`nav` 仍是 L2，
所以"复用登录态"不会降低后续写操作的门槛。

## 2. 服务类调优项

调优目录从 5 项扩到 **6 项**，新增：

| key | 类型 | 目标 | 需要管理员 |
|---|---|---|---|
| `service.diagtrack-manual` | service | `DiagTrack` StartMode → `Manual` | 是 |

配套改动（都在 `resource.ps1`）：

- `Get-TuneServiceState`：读 `StartMode`（CIM `Win32_Service`）+ `Status`（`Get-Service`）；
- 快照新增 `kind='service'`：记录 `existed / previousMode / previousStatus`；
- apply：`Set-Service -StartupType`，回读校验 `verified`；
- rollback：恢复 `StartupType`，快照时是 `Running` 就再 `Start-Service`；
- 未提权时计划直接 `blocked`（`requiresAdmin` 是通用机制，不需要额外分支）。

服务项**不在**冒烟里真实执行（改服务启动类型影响面太大），只验证"目录出现 + 未提权时计划 blocked"。

## 3. `apps.winget.plan` 已装检测精确化

CL-013 用的是"一次 `winget list` + Id 列子串匹配"，快但是启发式
（`Microsoft.PowerToys` 与 `Microsoft.PowerToys.Preview` 会互相污染）。

现在 `Get-WingetInstalledState` 有两个模式：

| Mode | 命令 | 特点 |
|---|---|---|
| `exact`（默认，ids ≤ 10） | 逐个 `winget list --id <id> -e` | 精确；每个 id 一次调用（~0.6s），返回 `exitCode` |
| `bulk` | 一次 `winget list` + 子串匹配 | 快；启发式，作为降级路径 |

判定不能只看退出码：winget 在"没有匹配"时可能返回 0 且输出 `No installed package found`，
所以同时检查退出码与输出关键字（含中文本地化字符串）。

`apps.winget.plan` 默认走 `exact`；ids 超过 10 个自动降级 `bulk`（避免 20 次调用）。

## 5. 边界

- `attach` 不做端口扫描，也不自动发现"用户是不是开着调试端口"——必须显式给端口。
- 服务项只有一个（DiagTrack），且没有"服务当前是否被依赖"的检查；停系统关键服务仍会被策略与系统本身挡住。
- `exact` 模式 ids > 10 会静默降级 `bulk`，返回值里的 `source` 会明确写 `winget-list-substring`，调用方可以据此判断精度。
