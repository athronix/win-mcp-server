# CL-017 跨请求等待（watch）与一次失败的事件订阅尝试（v0.14.0）

> 日期：2026-11-27 · 目标：把"等"从"占住一次请求轮询"升级为"arm 一次，之后按需查询"
> 参考：agent-desktop 的 `wait` 与 session 模型、CursorTouch 的 `WaitFor`

## 1. 结论先行

**UIA 事件订阅在本机不可用**，我不打算把它包装成"已实现"。证据在后文。所以这一轮交付的是
**跨请求 watch**——它解决的是同一个真实问题（长时间等待），但不依赖事件推送。

## 2. 为什么要跨请求

CL-015 的 `desktop.ui.wait` 已经很快（命中 ~86ms），但它有一个结构性限制：
**它占用一次请求**，而单次请求上限是 60 秒。等下载、等编译、等 CI 回调这类场景根本等不完，
调用方只能"多次调用 wait，每次超时再重试"，又把成本推回轮询。

`desktop.ui.watch`（L0 只读）把它拆成两步：

```jsonc
{"action":"arm","handle":-1,"text":"Notepad","maxDepth":2,"ttlMinutes":30}
// → {"watchId":"3838e095-…","alreadyMet":false,"expiresAt":"…"}

{"action":"status","watchId":"3838e095-…"}
// → {"matched":false,"waitedMs":1928,"checks":2}
// → {"matched":true,"waitedMs":4976,"checks":4,"ref":"@s1:e4","node":{...},"snapshotId":1}

{"action":"cancel","watchId":"…"}   // 或 {"action":"list"}
```

要点：

- **arm 只记条件**（窗口根 + text/role/automationId + disappear），不做阻塞；
- **status 做一次轻量扫描**（只读 ControlType/Name/AutomationId，命中早退），未命中就立刻返回；
- **命中后自动移除** watch，并用"命中元素所属窗口"做一次完整快照，返回可直接用的 ref；
- TTL 默认 30 分钟、容量上限 32 个，超出按创建时间淘汰最旧；
- `handle=-1` 表示整个桌面（**昂贵**，能传具体窗口句柄就别用）。

## 3. 事件订阅：试过什么，为什么放弃

期望很强：真正的事件回调能把 86ms 轮询变成 ~0ms 唤醒。实际过程：

| 尝试 | 结果 |
|---|---|
| 桥进程内订阅 `StructureChanged` + `AutomationFocusChanged`，用 WinForms `DoEvents()` 泵消息 | `hits=0`（10 秒，期间新开窗口） |
| 独立 `pwsh -STA` 进程 + `DoEvents` 泵 | `hits=0`（桌面根作用域，期间启动 notepad） |
| 同上，窗口作用域 + 真实菜单弹出（`Alt+F`） | `hits=0` |
| handler 用 scriptblock（怀疑 runspace 重入被拒）→ 换成 **C# 静态计数器委托** | 仍 `hits=0` |

同时排除了另一个干扰项：**桌面根快照里 `RootElement.NativeWindowHandle` 返回的是无意义句柄**
（实测指向某个 `csrss` 窗口），拿它去跑 Chromium settle 会枚举一堆无关子窗口并卡住。

结论：在"普通完整性进程 + 无 UIAccess + .NET `System.Windows.Automation` 客户端"这个组合下
拿不到事件回调。要真做到事件驱动，得上原生 `IUIAutomation::AddStructureChangedEventHandler`
（COM 手工绑定）或 WinEventHook，那是另一个量级的工程量，收益是把 86ms 变成 0ms——
**不值得现在做**，已在边界里写清。

## 4. 顺手删掉的"会卡死"的代码

CL-011 为了 Electron 的语义树做了两件事：请求 MSAA 对象、以 `Chrome_RenderWidgetHostHWND` 为根做 `FindAll`。
这一轮实测到它们会**卡住数十秒**（Electron 渲染进程不响应 UIA 树请求），且最终拿到的还是 0 个子节点。
所以整段删除，只保留"按窗口类名探测"用于告警：

```
warnings: 该窗口是 Chromium/Electron，渲染进程未开启可访问性，语义树只有外壳。
          可让应用以 --force-renderer-accessibility 启动，或改用 win-browser 的 CDP 通道。
```

代价是删掉了约 60 行"看起来很像能力"的代码；收益是 `desktop.ui.snapshot` 不再有超时风险。
**顺手修掉的真缺陷**：`Get-UiTree -Handle -1` 之前会走进 Chromium settle 分支，白等 250ms 后
用一个垃圾句柄遍历，返回 7 个节点且可能挂死；现在 `-1` 直接短路（`window.handle=0`，`renderHost=0`），
桌面根快照 48 节点、耗时正常。

## 6. 边界

- **不是事件驱动**：status 才检查，所以"命中延迟"取决于调用方查询频率（本次实测 400ms 一轮 → 命中在 5s 内）。
- **status 的成本与扫描范围成正比**：`handle=-1` + `maxDepth` 大时会明显变慢（一次几十~几百毫秒）。
- **watch 状态在进程内存里**：进程重启即失效；不做持久化（重启后重新 arm 即可）。
- **命中后无法回看**：watch 一经命中即移除，`status` 再查会 `INVALID_PARAMS`——这是有意的（避免陈旧 ref 被误用）。
- **仍然要重新快照**：返回的 ref 属于命中时那次快照，之后 UI 再变就必须重新快照。
