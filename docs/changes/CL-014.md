# CL-014 资源调优：声明式目录 + 快照 + 一键回滚（v0.11.0）

> 日期：2026-11-27 · 参考：AlexDo96/agentic-workstation-optimizer（`backup-and-rollback.ps1` 的快照 schema、
> 双文件 only-first-baseline、`null` 精确还原、按模式分级；`optimize-workstation.ps1` 的"备份作为强制前驱"）
> 以及 winutil-cn 的"声明式白名单解析器"（只允许受控 registry/service 动作）

## 1. 补的是什么

CL-006 的 win-resource 只有"看"（指标/磁盘/清理分析）和"清 TEMP"。缺**调优与回滚**：
改了系统设置之后没有办法一键退回去。这一轮把"可逆的批量写"补齐。

## 2. 声明式目录（硬编码白名单）

`packages/core/ps/modules/resource.ps1` 里的 `$script:TuneCatalog`，**5 项**：

| key | 类型 | 需要管理员 |
|---|---|---|
| `explorer.show-file-extensions` | HKCU registry (DWord) | 否 |
| `explorer.menu-delay` | HKCU registry (String) | 否 |
| `explorer.visual-effects` | HKCU registry (DWord) | 否 |
| `power.high-performance` | powercfg 方案 | 否 |
| `system.network-throttling` | HKLM registry (DWord) | 是 |

为什么硬编码而不是读配置文件：**可编辑的目录等于把"任意注册表写入"暴露给 LLM**。
想加一项必须改代码 + 过审，这是有意的成本。`resource.tune.plan` 只接受目录里的 key，
目录外的 key 直接 `blocked`（实测 `hack.anything` 被拒）。

## 3. 快照（照 agentic-workstation-optimizer）

`New-TuningSnapshot` 在**第一次修改之前**落盘：

```
%LOCALAPPDATA%\win-mcp\tune-snapshots\<GUID>.json
{schema, snapshotId, operation, machine, user, createdAt, elevated, entries:[...]}
```

entries 按类型：registry 记录 `existed / value / valueType`；power 记录 `previousScheme`。

**only-first-baseline**：另外写一份 `latest-snapshot.json`，但**只在它不存在时写**。
保证 latest 永远是"最初优化前"的基线，多次调优不会把它覆盖掉。

## 4. 应用与回滚

`Invoke-TuningApply`：

- 每一项都必须在快照里（快照没覆盖到的 key 一律拒绝执行——这是"可回滚"的前提）。
- `requiresAdmin` 且当前未提权 → 记 `ADMIN_REQUIRED` 跳过，**不静默忽略**。
- 逐项回填 `previousValue`（来自快照）与 `after`（写后回读），带 `verified`。

`Restore-TuningSnapshot`：

1. **逆序**恢复（同一项被多次改时先撤最后一次）；
2. 原本不存在 → `Remove-ItemProperty`，**不写默认值**；
3. 电源方案 `powercfg /setactive <previous>`；
4. 只接受 GUID，路径注入 `INVALID_PARAMS`（实测 `C:\Windows\win.ini` 被拒）；
5. 跨机（`machine` 不匹配）直接拒绝。

## 5. 能力面（resource 域 4 → 9）

| 能力 | 风险 | 说明 |
|---|---|---|
| `resource.tune.catalog` | L0 | 目录 + 当前值 + 本会话是否可应用 + 是否提权 |
| `resource.tune.plan` | L1 | 建快照 → planId（未知 key 不建快照；管理员项标 blocker） |
| `resource.tune.apply` | L2 | 按 planId 应用，keys 必须与预览一致 |
| `resource.tune.rollback` | L2 | 按 snapshotId 一键回滚 |
| `resource.tune.snapshots` | L0 | 快照列表 + 首次基线 latest |

计划复用 CL-013 的 `PlanStore`（规范化指纹 + 一次性 + TTL 5 分钟）。
`resource.tune.apply` 返回 `rollbackHint`，直接给出回滚参数，省得调用方自己拼。

## 6. 实测（真机，HKCU 可逆项）

```
TN-01 目录可读（count=5, elevated=false, menu-delay current=400）
TN-02 计划建立快照（status=ready, snapshotId 已生成）
TN-03 应用后 current=0，previousValue=400
TN-04 一键回滚后 current=400（等于原值）
TN-05 需要管理员但未提权 → blocked
TN-06 目录外 key → blocked
TN-07 路径注入 → INVALID_PARAMS
TN-08 blocked 计划执行 → PLAN_BLOCKED
TN-09 快照列表可读，latest 已写入
TN-10 keys 不一致 → PLAN_MISMATCH
```

单测：`packages/servers/tests/resource-tune.test.ts` 11 条（计划/应用/回滚/错误码/部分失败）。

## 7. 实现中修的一个缺陷

`resource.tune.plan` 最初对未知 key 仍然调用 `New-TuningSnapshot`，而快照函数会抛
`INVALID_PARAMS` —— 结果"计划"变成了报错，调用方拿不到结构化的 blockers。
改成：**未知 key 时不建快照**，直接返回 `blocked` + 原因（TN-06 就是被这条冒烟逼出来的）。

## 8. 边界（没有粉饰）

- **目录只有 5 项**：不是完整调优工具，只是把机制跑通；扩项要改代码。
- **不含服务启停调优**：服务只做了备份数据结构，目录里还没有服务类 tweak。
- **无重启提示**：部分项（如视觉效果）需要重启资源管理器/重启系统才生效，没有做检测与提示。
- **不做前后对比指标**：apply 只回读值，不采样"调优前后 CPU/帧率"，所以无法证明"真的变快了"。
- **快照不防篡改**：同用户可改，定位是"操作失误回退"，不是合规审计存储。
