# CL-015 等待机制与门控指示器（v0.12.0）

> 日期：2026-11-27 · 参考：agent-desktop 的 `wait` 命令与 `cursor-overlay`、
> CursorTouch 的琥珀边缘指示器、agent-browser 的"动作后重取快照"

## 1. 为什么"等待"是硬缺口

CL-011/012 交付后，所有自动化只有一种节奏：**调用方反复快照**。
代价是双重的：

- 每次轮询都是一次 tool call（客户端往返 + 审批链路过一遍）；
- 每次都要把整棵语义树传回来（几百节点），而真正关心的只有一个元素。

真实场景（点按钮后等结果、等下载完成、等弹窗消失）全都卡在这里。

## 2. `desktop.ui.wait`（L0）

| 参数 | 说明 |
|---|---|
| `text` | 元素名称包含（不区分大小写） |
| `role` | 角色精确匹配（button/textbox/…） |
| `automationId` | AutomationId 精确匹配 |
| `disappear` | true 表示等条件消失 |
| `timeoutMs` / `pollMs` | 默认 10000 / 250，最长 60000 |
| `maxNodes` / `maxDepth` | 每轮扫描上限 |

命中返回：`matched / waitedMs / polls / visited / snapshotId / ref / node`。
**ref 来自命中后那次完整快照**，可直接喂给 `desktop.ui.act`。
超时抛 `TIMEOUT`（带 polls、visited、条件原文与窗口标题，便于判断是"没出现"还是"找错窗口"）。

### 2.1 性能：为什么不能每轮都做完整快照

第一版直接用 `Get-UiTree` 轮询，实测 **命中一次要 4.8 秒**——因为完整快照对每个节点要探 7 个控件模式 + 读 bounds + 读 value。
改成两层：

1. `Find-UiElementFast`：只读 `ControlType / Name / AutomationId`，命中即返回（早退）；
2. 命中后**只做一次**完整快照，用来生成 ref。

同一窗口同一条件：**4835ms → 86ms**（236 节点全扫 miss 约 0.9s）。
另外 `Get-UiTree` 新增 `EnableRendererSettle` 开关：只在第一轮做 Chromium settle，避免每轮都 sleep。

## 3. `browser.cdp.wait`（L1）

条件在**页内**求值（`selector` / `text` / `urlContains`），Node 侧阻塞到超时：

- 首次立即检查一次，之后按 `pollMs` 轮询；
- 命中后附带一份新快照（`withSnapshot=false` 可关），ref 直接可用；
- 超时抛 `TIMEOUT`，提示"先快照看实际状态再决定是否重试"——**不自动重试导航/动作**。

为什么不直接用 CDP 的 `Page.waitForSelector`：CDP 没有这个名字，等价能力要靠 `Runtime.evaluate` 里跑等待脚本（我们就是这么做的），
好处是三个条件可以任意组合，且失败原因能带回来。

## 4. 门控视觉指示器

`ps/control-indicator.ps1` + `core/desktop/indicator.ts`：

- 四条琥珀色边框（虚拟屏幕四边）+ 顶部一行说明 `AI 控制桌面中 - 移动鼠标可夺回`；
- 窗口样式 `WS_EX_TRANSPARENT | WS_EX_LAYERED | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`：
  **点击穿透、不抢焦点、不进任务栏**；
- 独立进程，`hide()` 直接 kill；进程自然到期也会自己退出；
- 生命周期绑定租约：`lease-acquired` 点亮，`release / user-steal / lease-expired` 熄灭；
- **纯装饰**：spawn 失败只写一行 stderr，绝不影响门控判定（`I-06` 单测固定这个行为）；
- `WIN_MCP_DESKTOP_INDICATOR=0` 可关闭（无人值守/录屏场景）。

## 5. 覆盖测试顺手抓到的漏登记

`desktop.ui.wait` 上线时，`D-01` 的门控表覆盖断言直接失败：

```
expected [ 'desktop.ui.wait' ] to deeply equal []
```

即新能力没登记 `CONTROL_TABLE`，按 fail-closed 会被判成 `direct`——一个纯读的等待会逼用户点同意弹窗。
补登记为 `other` 后通过。这条测试就是为这种"新增能力忘了分类"准备的。

## 7. 边界

- **UIA 等待是轮询不是事件订阅**：`Automation.AddAutomationEventHandler` 能做真事件，但跨进程 COM 事件 + STA 线程管理在本项目里成本过高，
  当前先用"轻量扫描 + 早退"把成本压到可接受（命中 ~86ms）。
- **指示器不是安全边界**：用户看不到/关掉它也不影响门控判定，它只是提示。
- **`visited` 只是本轮扫描节点数**，不是全树大小（截断时不代表窗口真的只有这么多节点）。
- **wait 不产生审批**：L0/L1 只读，所以不需要用户同意；但也因此不能用来"等某个危险操作完成"。
